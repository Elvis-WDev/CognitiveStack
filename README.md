Software engineering specifications, prompt architectures, and modular skills for building
agentic systems.

`agent-skills` · `prompt-engineering` · `system-architecture` · `llm` · `workflows`

## What It Is

CognitiveStack is a Markdown knowledge system that a project installs next to its code, so
AI agents know how to work before they change anything.

This edition targets Windows desktop applications built with C# 14 on .NET 10 LTS, WPF with
MVVM, and SQLite with Dapper.

It is not a code starter and not a library. It is the context layer: engineering
specifications, architectural boundaries, interface criteria, quality and security rules,
and reusable skills, written so that Codex, Claude, GitHub Copilot, or any other agent read
the same thing and reach the same decisions.

It works with [OpenSpec](https://github.com/Fission-AI/OpenSpec) under one rule:
**CognitiveStack governs engineering. OpenSpec governs change.** CognitiveStack defines how
agents build; OpenSpec defines what is being changed, from the proposal to the archived
record of what shipped.

## Why It Exists

An agent writes code quickly, but without persistent context it tends to:

- invent a different pattern in every module;
- mix business rules with infrastructure;
- duplicate components and documentation;
- build interfaces straight from the database schema;
- expose technical detail on screen;
- skip states, permissions, tests, or migrations;
- rely on conversations the next agent never saw.

CognitiveStack turns those decisions into versioned, navigable, verifiable instructions
inside the repository itself.

### Skills

Procedures loaded only when a task needs them. Workflow skills control the process;
specialist skills control the disciplines.

- **Workflow**, generated by OpenSpec: `explore` · `propose` · `update` · `apply` · `verify`
  · `sync` · `archive`
- **Specialist**, in `.agents/skills/`: `implement-wpf-screen` · `create-migration`
  · `review-code` · `harden-security` · `optimize-performance` · `update-documentation`
  · `commit-changes`

## Reference Stack

| Layer        | Choice                                                                |
| ------------ | --------------------------------------------------------------------- |
| Language     | C# 14                                                                 |
| Framework    | .NET 10 LTS, composed with the Generic Host                           |
| Interface    | WPF and XAML with MVVM through CommunityToolkit.Mvvm                  |
| Persistence  | SQLite through Microsoft.Data.Sqlite, with Dapper                     |
| Integrations | `HttpClient` through `IHttpClientFactory`, MailKit for SMTP           |
| Testing      | xUnit, real SQLite databases, Mailpit as the SMTP sink                |
| Packages     | NuGet with Central Package Management, lock files, and NuGet Audit    |
| Development  | Linux with VS Code or Zed, Wine smoke runs, acceptance on Windows     |

Projects follow one dependency direction:

```text
Desktop (WPF) -> Presentation (ViewModels) -> Application (use cases) -> Domain
Desktop       -> Infrastructure (SQLite, HTTP, SMTP, files)  -> Application
```

Docker runs only auxiliary tools, such as Mailpit. OpenSpec is a Node.js developer tool and
never becomes a dependency of the solution.

The stack is a default decision, not an irreversible constraint. A project that needs to
deviate records the reason and its consequences in an ADR.

## How The Context Works

```text
AGENTS.md
  -> states what to read and how to work
ARCHITECTURE.md
  -> shows components, boundaries, and dependencies
docs/product/
  -> explains what the product must do
docs/architecture/
  -> explains how it must be built
openspec/
  -> specifies current behavior and the changes in progress
.agents/skills/
  -> runs repeatable procedures
docs/quality/ + docs/security/
  -> defines when a change is acceptable
```

Every non-trivial behavior change runs through one lifecycle:

```text
explore -> propose -> review -> apply -> verify -> archive
```

OpenSpec writes the proposal, specs, design, and tasks; `openspec/config.yaml` requires each
design to answer CognitiveStack's screen and sensitive-operation briefs; each task runs
through the specialist skill for its discipline; and archiving merges the shipped behavior
into `openspec/specs/`.

The point is not to load the whole repository into every prompt. An agent starts from a
small map and opens only the source of truth the task requires.

## Working With OpenSpec

OpenSpec ships already initialized for Codex, Claude Code, and GitHub Copilot. It replaces
the earlier `docs/plans/` folder and the feature templates in `docs/product/features/`:
current behavior now lives in `openspec/specs/`, and each change in progress lives in
`openspec/changes/<change>/` with its proposal, delta specs, design, and tasks.

### Each Knowledge In One Place

```text
docs/product/        why the product exists
openspec/specs/      what the system does
docs/architecture/   how the system is structured
code                 how it is implemented
```

### When To Open A Change

Open an OpenSpec change for non-trivial work that alters observable behavior: a new
capability, a changed or removed requirement, a new screen or workflow, or a new API
contract. Typo fixes, refactors, dependency upgrades, formatting, and documentation-only
edits do not need one.

| Workflow | Claude Code     | GitHub Copilot  | Codex                      |
| -------- | --------------- | --------------- | -------------------------- |
| Explore  | `/opsx:explore` | `/opsx-explore` | `$openspec-explore`        |
| Propose  | `/opsx:propose` | `/opsx-propose` | `$openspec-propose`        |
| Update   | `/opsx:update`  | `/opsx-update`  | `$openspec-update-change`  |
| Apply    | `/opsx:apply`   | `/opsx-apply`   | `$openspec-apply-change`   |
| Verify   | `/opsx:verify`  | `/opsx-verify`  | `$openspec-verify-change`  |
| Sync     | `/opsx:sync`    | `/opsx-sync`    | `$openspec-sync-specs`     |
| Archive  | `/opsx:archive` | `/opsx-archive` | `$openspec-archive-change` |

A person reviews the proposal, specs, design, and tasks before any code exists. Each task
then runs through its specialist skill, and a change is archived only when implementation,
specs, tests, and documentation agree.

### Machine Setup

Each developer installs the CLI and enables the full workflow profile once:

```bash
npm install --global @fission-ai/openspec
openspec config set profile custom
openspec config set workflows '["propose","explore","apply","update","sync","archive","verify"]'
openspec update
```

The `verify` workflow is outside OpenSpec's default profile; without the custom profile,
`openspec update` removes the verify skills from the repository.

### Generated And Authored Files

- Generated, never edited by hand: the `openspec-*` skills in `.agents/skills/`,
  `.claude/skills/`, and `.github/skills/`, the commands in `.claude/commands/opsx/`, and the
  prompts in `.github/prompts/`. Regenerate them with `openspec update` after upgrading the CLI.
- Authored: `openspec/config.yaml`, the bridge that injects CognitiveStack's rules into every
  OpenSpec run, and the specs and changes themselves.

The full lifecycle, spec-writing rules, and commit order are in
`docs/quality/change-lifecycle.md`; adding OpenSpec to a new project is in
`docs/architecture/bootstrap.md`.

## Core Criteria

The core rules assume the PC is outside our control and that every operation can be
repeated, interrupted, or raced. A command that runs twice must not act twice, and a crash
must never leave half a sale:

- keep `Domain` free of frameworks, and keep SQL inside `Infrastructure`;
- use `decimal` for money with explicit rounding, and inject the clock;
- wrap every multi-step write in one transaction, and back invariants with constraints;
- enforce permissions in use cases, denied by default; a disabled button is presentation only;
- make side effects idempotent, and run external calls after the local commit as persisted
  pending operations;
- after an ambiguous external failure, query the status of the same operation before retrying;
- apply versioned migrations after a verified backup, and practice restore;
- keep data out of the installation folder, and never share a SQLite file over the network;
- keep secrets out of the repository, configuration, and logs, and verify every signed update
  and license.

## Interface Criteria

The interface rules keep an operational panel from becoming a pile of cards, filters, and
messages. Designing is deciding what does not appear:

- answer in writing who uses the screen, what they decide, with what information, and what
  their single primary action is, before implementing it;
- design from the user's job, never from the database schema;
- never show a value only because a use case returns it;
- tier information P0 to P3, and keep technical detail out of the initial view;
- limit simultaneous actions: one primary, one or two secondary, the rest disclosed;
- choose each control from the user's intent, not the data type: steppers, sliders, segmented
  controls, selection cards, chips, and searchable comboboxes each fit a different task;
- avoid both under-designed forms of generic inputs and over-designed custom widgets;
- take spacing, type, color, radius, and motion values from the XAML tokens;
- cover every state: loading, empty, partial, error, permission, and success;
- keep the UI thread free of I/O, page queries, and virtualize grids;
- verify keyboard, touch, display scaling, light, dark, and high contrast before calling
  anything done.
